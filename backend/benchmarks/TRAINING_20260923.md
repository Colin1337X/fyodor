## Audit

The existing C training engine already implemented reverse-mode autodiff,
random LLaMA initialization, dense LLaMA/Gemma import, full-weight CPT/SFT,
LoRA, DPO, clipped transactional AdamW, checksummed optimizer checkpoints,
GGUF export/reload and a desktop launcher. Existing tests covered finite
differences, convergence, exact resumed trajectories and Gemma graph features.
The initial CPU suite passed 42 tests with four unavailable ROCm/MLX hardware
tests skipped (46 registered). Training is CPU F32; it is not GPU resident.

Important gaps remain: persistent training execution plans, accelerator backward,
mixed precision, production dataset streaming/packing/shuffling, runner-level
microbatch accumulation, schedules, validation runs, periodic checkpoints and
graceful desktop cancellation. The C API already accumulates parameter gradients
across graphs, but the CLI does not yet expose accumulation groups. Stop in the
desktop still terminates the process; checkpoints are written at normal run end.
No unsupported controls or HTTP training endpoints were added.

## Changes and numerical contract

* Dense linear forward reuses a weight across four token accumulators. Each
  retains the original ascending **double** reduction followed by an F32 store.
* Dense backward separates input and weight adjoints, giving each a contiguous
  inner loop and cache-friendly order. Each destination retains the original
  F32 addition order. Shared parameter storage takes the original interleaved
  path, including distinct leaves borrowing the same parameter.
* Attention accumulates four adjacent value lanes, skips known causal future
  entries, and caches the double `dP` dot products for one row during backward.
  The probability matrix and masking semantics are unchanged. Scratch costs
  eight bytes per sequence position per attention node; it is budgeted and freed.
* Frozen-matrix backward reuses a single decoded row across tokens, using
  Fyodor's existing CPU SIMD decoders where available. The graph allocates one
  maximum-width row only after forward construction. No headroom/allocation
  means the original scalar backward still runs. Scalar-ISA builds also retain
  row reuse using scalar decoding. Every destination preserves its addition order.
* Frozen-matrix forward reuses 256-value decoded tiles across four tokens.
  Quantized weights retain the original F32 reduction, including Q4_0's low/high interleaving,
  and scalar token tails. The scratch is a bounded 1 KiB stack buffer; scalar
  ISA or fewer than four tokens retains the existing forward kernel. Seven-format
  exact forward checks cover token tails, full tiles, multiple quant blocks and
  odd F32/F16/BF16 row widths.
* The scalar F32 inference projection now accumulates in double. Mapped F32
  training uses the same rule, consistent with dense F32 training. This fixes
  reference drift on long F32 projections; a cancellation fixture checks the
  exact result of `1e8 + 1 - 1e8`, including four-token tiling and a scalar tail.
  Imported F32 training can therefore differ from the earlier F32-accumulation
  implementation. Quantized training retains its arithmetic order.
* CLI resume validates a versioned fingerprint of data, effective model/config,
  objective and frozen base before restoring state. Shape equality alone was
  insufficient. The low-level checkpoint format is unchanged; older CLI files
  without the run identity header are deliberately rejected, not guessed safe.
* `--metrics` writes per-update CSV. Optional `NYA_TRAIN_PROFILE=1` emits
  allocation counts and operation timings. Flushed progress reaches the desktop
  during a run; the existing UI now displays measured throughput and graph memory.

No tolerance was loosened. New scalar oracles require bitwise dense forward and
gradient equality, including tails, one frozen operand, aliased parameters and
two-graph accumulation. Seven mapped formats compare gradients exactly against
the scalar tensor-value oracle, both with scratch and with an exactly full graph
budget. Attention finite differences cover head widths 3/4/5/7/8/9, grouped heads,
causal/local masking and positive vision groups at the existing 0.0003 tolerance.

## Measurement method

Windows 11, Ryzen 5 9600X, six exposed logical processors; GCC 16.2, C17 Release
`-O3`, no fast-math, single-thread training loops with baseline compiler SIMD and
runtime-selected native quantized decoders. This is an interactive desktop, not
an isolated thermal/power-controlled host. Training runs are serial, with no builds
or tests during the accepted comparisons. No GPU training throughput is claimed.

[`train_compare.py`](train_compare.py) starts fresh deterministic runs, alternates
before/after and after/before order, preserves each CSV/log/command and executable
hash, and rejects differing per-step losses or exported model hashes. Each
synthetic comparison has four process repetitions, 14 updates per process, with
the first two updates excluded from timing. Each process contributes one
tokens/sec sample (total measured tokens divided by total step time); tables
report arithmetic mean ± sample SD of those four samples. The warmup updates
remain part of the exact training trajectory.

Step time includes zeroing, graph creation/free, forward/loss, backward and
AdamW. It excludes tokenization, reference-policy preparation, model load,
checkpoint/export and logging. Full process elapsed time is separately retained.
Graph bytes do not include parameter/master/optimizer state, mapped weights,
dataset storage, stack temporaries or process overhead. Peak RSS, CPU utilization,
transfer counters and per-phase checkpoint/export latency are not yet measured.
Do not mistake graph bytes for peak RAM. The initial attempted GCC `-pg` profile
returned no samples on this host; its raw output is retained but was not used.

## Real-model result and reference correction

TinyLlama 1.1B Chat Q4_K_M, SHA-256
`9fecc3b3cd76bba89d504f29b616eedf7da85b96540e490ca5824d3f7d2776a0`,
was imported for rank-2 LoRA CPT, checkpointed and exported as a 4,400,929,248-byte
F32 GGUF. A short two-update diagnostic used four actual tokens per step. Losses
were 5.51412201 and 3.06696653 before and after mapped-backward optimization.
Both optimizer checkpoint and exported model matched byte for byte:
checkpoint `d8488ae23794f58e0694a39d24f103e19f53e7b8a2e686d8889c38228e094007`,
model `ab6ceecda108e7070b5af188c2362049ebee9fa87b3680f93ea2dd48876afac8`.
The diagnostic after-run overlapped an inference investigation, so its timing
is not accepted as an isolated performance comparison. Controlled real-model
measurements are retained separately in `training-20260923/real-paired`.
That comparison uses three updates of eight tokens, excludes update one as
warmup, and runs two fresh processes per version in forward/reverse order.
Mapped-backward optimization improves 0.7713 ± 0.0058 to 1.7809 ± 0.0083 tokens/s;
mean backward falls from 6515.98 to 647.08 ms. Forward remains about 3.8 seconds,
which motivates the subsequent mapped-forward tile change. The very small
sample count and workload do not establish general large-model throughput.

The subsequent [combined mapped-forward/backward comparison](training-20260923/real-final/metadata.json)
uses the same methodology and exact checks: 0.8044 ± 0.0467 before versus
4.5122 ± 0.0008 tokens/s after (5.61×). Mean forward falls from 3676.47 to
1141.40 ms, backward from 6259.39 to 606.64 ms, whole step from 9961.92 to
1772.95 ms. All eight per-run loss trajectories/export hashes across the two
real-model comparison experiments agree. This small-context workload remains
slow in absolute terms and does not substitute for a long training run.

The exported model initially passed reference inference and optimized graph
execution with `NYA_CPU_ISA=scalar` at prefixes 8/7/6, all logits exactly equal.
Default SIMD inference initially failed the existing scaled-error 0.001 bound at prefix 8:
max absolute 0.002895713, RMS 0.000721422, max scaled 0.002289755.
The output weights are identical to the earlier implementation. A separate
diagnostic executable then used double accumulation in scalar F32 projections,
leaving the optimized path unchanged. It passed the existing bound, identifying
serial F32 accumulation drift as the main discrepancy. Production scalar F32
projections now use double accumulation, aligned with dense training. The
corrected test passes prefixes 8/7/6: worst max absolute 0.000662566, RMS
0.000160221, scaled error 0.000503736. The original failure, diagnostic probe and
corrected logs are all retained. No threshold was changed and the SIMD inference
kernel was not changed to fit this case. This is a higher-precision projection
oracle, not an assertion that every transformer operation runs in float64.

### Native CUDA F32 export accuracy

The exported model also exposed long-reduction drift in CPU RMS normalization
and native CUDA F32 prefill. The scalar CPU RMS sum and squares now use double,
matching training; a direct regression checks finite `1e20` activations whose
F32 squares previously overflowed. CUDA F32 GEMM now uses two independent F32
accumulation chains per output, then combines them. Other weight formats retain
their original reduction. This is an accuracy correction, not a precision-mode
or tolerance change. It requires neither cuBLAS nor CUTLASS.

With the corrected RMS reference, the original native CUDA kernel fails prefix
8 at scaled error 0.00269917. Two chains pass prefixes 8/7/6 with worst scaled
error 0.000199958, and prefixes 65/64/63 with worst scaled error 0.000011664.
Both 32- and 64-output tile paths are therefore checked on the trained export.
The existing bound remains 0.001. The logs retain original failures and probes.
The final optimized CPU path also passes prefixes 8/7/6, with worst scaled
error 0.000678329 against the corrected RMS/projection reference.
An early source-restoration experiment reused a stale embedded kernel because
the restored file retained its old timestamp; explicit CMake regeneration and
byte comparison of the embedded source corrected the experiment before acceptance.

The accuracy fix has a measured performance cost. The following native-only
comparison uses the F32 trained model above, F32 KV, two warmups and five measured
repetitions in each forward/reverse order. Values pool ten throughput samples,
reporting mean ± sample SD. Model loading is excluded; decode requests 16 tokens.
The desktop GPU remains active at roughly 10% between runs; these are local
comparisons, not isolated-device peak claims.

| Native F32 prefill | Original tokens/s | Two-chain tokens/s | Change |
|---|---:|---:|---:|
| 8 tokens | 145.59 ± 1.49 | 139.97 ± 2.17 | −3.9% |
| 33 tokens | 547.74 ± 5.33 | 495.42 ± 3.07 | −9.6% |
| 128 tokens | 1461.32 ± 8.50 | 1398.21 ± 5.91 | −4.3% |

[Commands, binary/model hashes and telemetry](training-20260923/f32-native-two/metadata.json)

## Reproduce

```sh
python backend/benchmarks/train_compare.py --before /path/to/before/fyodor-train --after /path/to/after/fyodor-train --output /new/evidence/directory
python backend/benchmarks/train_compare.py --before /path/to/before/fyodor-train --after /path/to/after/fyodor-train --base /path/to/tinyllama.gguf --steps 3 --warmup 1 --repetitions 2 --output /new/real-model/evidence
```

Both executables must support `--metrics`. The local baseline binaries and hashes
are identified in the manifests. `training-20260923/before-training.c` retains the
original training implementation for a separate source-copy build with the new
timing-capable CLI; do not replace files in a working checkout merely to benchmark.
Use Release `-O3`, the same compiler, data, seed, precision, environment and workload.
The bundled local `validate.py` driver is specific to the toolchain paths in this
workspace; it is development tooling, not a portable end-user installation script.

## Upstream study and provenance

Reviewed PyTorch's `aten/src/ATen/native/Linear.cpp` (upstream main as read on
2026-09-23), specifically flattening and `matmul(input, weight.t())` / `addmm`
dispatch, and its BSD-style license. Reviewed llama.cpp/ggml MIT-licensed
`ggml/src/ggml-cpu/ggml-cpu.c`, `ggml_compute_forward_mul_mat_one_chunk`, at
`5266f24da75dc449bd56cbed7addb9c8e4a6a73e`: row/column tiles, reusable converted
operands, and type-specific dot dispatch. Neither framework's tensor/runtime
machinery was suitable to transplant into this eager C graph.

These changes are original Fyodor C implementations of matrix algebra, loop
tiling/reuse and softmax differentiation, reusing Fyodor's existing dequantizers.
No upstream source was substantially adapted or linked, so no new redistributed
third-party source/license bundle is introduced. C++, PyTorch, BLAS and Python
are not required for training. Python is only the comparison driver.

Sources: [PyTorch Linear.cpp](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/Linear.cpp),
[PyTorch license](https://github.com/pytorch/pytorch/blob/main/LICENSE),
[pinned ggml CPU source](https://github.com/ggml-org/llama.cpp/blob/5266f24da75dc449bd56cbed7addb9c8e4a6a73e/ggml/src/ggml-cpu/ggml-cpu.c).
