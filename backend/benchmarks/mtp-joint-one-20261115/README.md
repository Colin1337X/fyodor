# Joint base plus one proposal: isolated C scheduling experiment

The current three-proposal joint path trades first-proposal early rejection for
one batched target traversal. This candidate reserves only one proposal beside
the already-emitted base token. It may reduce discarded target/assistant work,
but also reduces reuse of weights across verification tokens and requires more
rounds. No speedup is assumed or accepted.

joint_base.py retains the validated v2 eligibility and post-prefill fallback
checks, greedy-only selection, frozen assistant prefix, rewind/replacement,
output bounds and RNG behavior. The generated core differs from the preceding
v2 core by exactly one assignment: eligible joint requests use proposal window
one. Requested speculative window remains four as the diagnostic selector;
other requested windows and non-greedy paths are unchanged. Production core,
provider source, archive and defaults are unchanged. Host implementation is C.

Strict C17/C23 builds passed. Architecture and 22-case stopping-boundary suites
passed in both standards for CPU, GPU ring KV, GPU linear KV and forced CUDA
failure. GPU ring/linear require exact proposal-window-one selection; CPU and
failure require fallback. The existing boundary suite checks token limits,
all fixture EOS IDs, byte limits, matched errors and context stops.

The real Gemma short-context diagnostic passed twelve ordered ordinary,
serial-two, batch-two and joint-one cases, with 25 prompt tokens, 32 outputs,
and identical generated bytes/stop behavior. All three joint rounds report
16 drafted tokens, 14 accepted drafts and 59 total evaluated target positions
(including prompt ingestion). The earlier joint-three observation evaluated
68 positions, but it is not a matched performance comparison: batching/reuse
and pipeline differences matter. Model identity is checked before launch.
verification.json independently rechecked 74 recorded build/test files after
the run. These are correctness and work-count observations only.

This initial scheduling experiment links the same production provider archive
as the preceding joint-v2 experiment, not the later isolated Q6/Q4 kernel
candidates. Do not compare its raw times directly with those newer candidates.
Next requirements are long-context output parity, sanitizer validation, and a
matched same-provider joint-three/joint-one comparison before any integration.
No accepted llama.cpp or PyTorch score changes. Accepted llama.cpp ratios remain
85.61025294% short and 106.8707255% at 8K; the requested 125% target is unmet.
