# Gradient accumulation — September 24, 2026

This extends the [September 23–24 native training work](TRAINING_20260923.md)
in the existing uncommitted tree based on `ec3f6fa0437a3069a8ccd599ffe5cb9ef6497667`.
The core remains C17/C23 with GCC Release `-O3`. No C++ runtime or external
training framework is introduced.

## Behavior

The CLI and desktop now expose `--accumulate N`, 1–1024, default 1. Each update
processes N independent corpus windows, SFT records or DPO pairs. It retains one
sequence graph, or one chosen/rejected pair, then frees that graph after backward.
Parameter gradients persist across microbatches. AdamW, clipping, weight decay,
moments and optimizer step advance once per complete group.

Pretraining/CPT/SFT use a mean over all supervised tokens in the group. A short
window or completion is weighted by its actual unmasked target count, rather
than being given the same weight as a longer sequence. DPO averages preference
pairs, preserving the sequence-sum log probabilities inside each pair objective.
The monitoring loss uses double weighted addition; loss seeds and parameter
gradients remain F32. A combined graph may differ in last bits because its
reverse traversal adds parameter gradients in the opposite sequence order.

The loader still visits examples in file order. Groups wrap across the end,
including when accumulation exceeds the number of examples; no tail is dropped.
Resume calculates the next example from the saved optimizer step and accumulation
setting with overflow-safe modular arithmetic. Changing accumulation on resume
is rejected by the run fingerprint. Default-one fingerprints remain unchanged,
so existing versioned single-sequence checkpoints remain usable.

CSV metrics append `microbatches` and `loss_units`. The latter is the objective
denominator: supervised tokens for cross entropy, pairs for DPO. Forward/backward
times sum the microbatches; graph bytes report their maximum. Processed-token
throughput includes masked prompt work and both DPO branches. A failed backward
clears the incomplete group's gradients and does not apply a partial update.

This enables a larger effective batch under the same graph-memory budget. It
does not implement parallel sequence batching, packing, GPU training, shuffling,
schedules or evaluation. Changing effective batch changes the training trajectory;
no claim of identical convergence per update is made for different N.

## Correctness evidence

`test_train_runner.c` compares the actual runner with an independently assembled
single combined graph. Two unequal masked sequences have two and four supervised
targets. The DPO case uses different chosen/rejected lengths and fixed reference
log probabilities. Three updates compare losses, every gradient and every
parameter with clipping at 0.03 and default AdamW weight decay. Existing kernel
tolerances are unchanged; this new accumulation comparison uses 2e-6 absolute
bounds. Observed worst errors were 1.1920929e-7 for gradients and 3.7252903e-9
for parameters ([log](training-20260924/combined-graph.log)).

The runner is constrained to the exact largest single-microbatch graph budget;
the combined reference graph exceeds that budget. A second test admits the first
microbatch and deliberately rejects the second for memory. Weights and optimizer
step remain at the prior update; every accumulated gradient is zero afterward.
Selection tests also cover counters at `UINT64_MAX` and `SIZE_MAX`.

CLI tests compare byte-identical checkpoints and GGUFs after two updates plus a
new-process three-update resume versus five uninterrupted updates, for pretrain,
CPT, SFT and DPO. Unequal structured records and corpus tails cross group/dataset
boundaries. Changed accumulation, zero, negative, fractional, excessive and
overflowing option values are rejected.

The preserved previous executable independently verifies default-one compatibility
in all four modes: complete checkpoints and exported GGUFs match byte for byte.
Both executables also resume the exact same older `NYARUN` v1 checkpoint and
produce byte-identical results. [Commands and hashes](training-20260924/default-compatibility.json)
are generated by `verify_default.py`; `before-train-main.c` retains the old runner.

The [random-init lifecycle](training-20260924/lifecycle.json) runs accumulation 3
for 100 updates, and independently runs 40 updates, exits, reconstructs state,
then resumes for 60. Every loss, the final checkpoint and GGUF match exactly.
Loss falls from 5.59592517 to 0.000776006168. A separately launched native HTTP
server loads the resumed export and returns the expected greedy `bcabcabc`
completion for prompt `a`. Its ephemeral authentication token is not logged.

The Rust desktop test checks older JSON arguments that omit accumulation, bounds,
fractional/negative rejection and the argument passed to the native executable.
It passed in the release build. `serde_json` is an existing transitive dependency;
its new direct declaration is development-only for this test.

loops with runtime-selected decoders. Four fresh processes per version, fourteen
updates each, first two excluded from timing; before/after order alternates.
Runs were serial, with no builds or other validation during measurement. Mean
and sample SD use one token-rate sample per process, as in the preceding report.

All per-update losses and exported-model hashes match exactly. This shows no

TinyLlama 1.1B Q4_K_M, SHA-256
`9fecc3b3cd76bba89d504f29b616eedf7da85b96540e490ca5824d3f7d2776a0`,
rank-2 CPT, context 8, accumulation 3. The short retained corpus produces two
unequal windows. Update one processes 21 tokens, update two 18; losses are
3.65853789 and 3.13158978. A process exit/reinitialization between updates yields

* Checkpoint: `ae503658320cedd4ed8e75ba41db6e444df918eaa4f84eb17e13e9fbab2d1127`.
* F32 GGUF: `ca9d1933acffdc0bca4bba383e8093480df12d02df005fe36fd01769123be824`.

Each update peaks at 143,521,392 graph bytes. The uninterrupted process peaks at
812,433,408 working-set bytes, including mapped/shared pages, and 180,056,064
sampled private-commit bytes. Windows `K32GetProcessMemoryInfo` is polled every
50 ms; working-set peak is the largest observed OS high-water mark before exit,
private commit is the largest sample. These whole-process figures include model load, checkpoint and export.
They do not measure VRAM or sum to a total. This is a resource/correctness run,
not a controlled throughput comparison. Full logs, commands, CSV and methodology
are in [real-accumulation.json](training-20260924/real-accumulation.json).

The accumulated export passes prefixes 8/7/6 against the corrected scalar
reference: worst scaled error 0.000370738 on optimized CPU and 0.000129928 on
native CUDA with cuBLAS/CUTLASS disabled. The existing bound is 0.001. These
short runs prove execution and resume fidelity, not useful language convergence.

## Source study and provenance

Reviewed PyTorch's [gradient-accumulation guidance](https://docs.pytorch.org/docs/2.14/notes/amp_examples.html#gradient-accumulation)
for effective-batch optimizer/clipping boundaries, and
[`LossNLL.cpp`](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/LossNLL.cpp)
as read on September 24 for mean reduction using the non-ignored target weight.
Those principles motivated weighting by supervised tokens rather than blindly
dividing every sequence loss by N. The C implementation is original Fyodor code;
no upstream source was copied or linked, and no PyTorch dependency was added.
